## 1. 멱등키 (ADR 0001)

| | 토스페이먼츠 | Brandur (Stripe식) | WeFin |
|---|---|---|---|
| 저장소 | 서버 DB | Postgres `idempotency_keys` | Postgres `order_idempotency` |
| 키 범위 | 키 + API 키 + 주소 + 메서드 | (user_id, key) | (계좌, 키), 매수·매도는 지문으로 구분 |
| 처리 중 같은 키 | 409 | 409 | 409 |
| 같은 키, 다른 내용 | 422 | 409 | 422 |
| 처리 중 서버가 죽음 | 문서에 없음 | `locked_at` 만료 뒤 다른 요청이 이어받음 | 60초 만료 뒤 다시 선점, 펜싱 토큰으로 늦게 끝난 원래 요청 롤백 |
| 보관 기간 | 15일 | 약 72시간 | 24시간 |
| 여러 단계 처리 | 문서에 없음 | 단계마다 recovery point 저장, 재시도는 멈춘 단계부터 | 단계 구분 없음 |

**같은 점.** 키를 DB에 저장하고 저장된 응답을 그대로 돌려주는 구조, 처리 중 409, 사용자 단위 키 범위는 두 글과 같습니다. 다른 내용 422는 토스페이먼츠와 같습니다.

**다른 점과 이유.**
- Brandur는 요청 하나가 외부 결제(Stripe 청구)와 이메일 발송까지 이어져, 단계마다 recovery point를 저장하고 외부 호출에도 멱등키를 넘깁니다. WeFin 주문은 외부에 상태를 바꾸는 호출이 없습니다. 한투 호출은 시세 조회(읽기)뿐이고, 상태 변경은 주문 트랜잭션 하나에서 끝납니다. 그래서 중간 단계를 저장할 필요가 없고, 완료 처리를 주문과 같은 트랜잭션에 넣는 것으로 충분합니다. **적용하지 않음.**
- Brandur는 만료된 잠금을 이어받는 것까지만 설명하고, 늦게 끝난 원래 요청이 결과를 덮는 문제는 다루지 않습니다. WeFin은 이 문제를 코드 리뷰에서 지적받아 펜싱 토큰을 추가했습니다(ADR 0001 2.5.1).
- 보관 기간은 토스페이먼츠 15일, Brandur 72시간, WeFin 24시간입니다. 토스페이먼츠는 가맹점 서버가 다음 날 배치로 재시도하는 경우까지 받아야 하지만, WeFin의 클라이언트는 사용자가 보고 있는 화면 하나라 재시도는 몇 초에서 몇 분 안에 끝납니다. **24시간 유지.**

## 2. 원장과 대사 (ADR 0002)

| | 토스 결제 원장 | Stripe Ledger | WeFin |
|---|---|---|---|
| 원장 구조 | INSERT만 (취소도 INSERT) | 불변 이벤트 로그, 복식부기 | INSERT만, 단식부기 |
| 검증 | 5분마다 검증 배치 | clearing 계정이 0인지, 누락·지연 지표 | 하루 한 번 계좌 대사 + 주문 대사 |
| 불일치 처리 | 마이그레이션 중에는 구원장을 정답으로 자동 보정 | 자동 보정하지 않음. 원인 추적 후 검토를 거쳐 되돌리고 다시 처리 | 자동 보정하지 않음 |

**같은 점.** 원장을 INSERT만 하는 이유(이력 추적, 수정 경합 없음)는 토스 글과 같습니다. 자동으로 고치지 않고 원인을 먼저 찾는 것은 Stripe와 같습니다.

**다른 점과 이유.**
- 토스는 신·구 원장을 함께 운영하던 기간이라 구원장이라는 정답이 있었고, 그래서 5분마다 자동 보정할 수 있었습니다. WeFin에는 잔고와 원장 외에 정답으로 삼을 세 번째 기록이 없습니다. 잔고가 틀렸는지 원장이 빠졌는지 원인을 봐야 알기 때문에 자동 보정하지 않습니다.
- Stripe는 복식부기로 중간 계정이 0이 되는지 봅니다. WeFin의 현금은 사용자 계좌와 시장 사이에서만 움직여 중간 계정이 없고, 복식부기로 바꿔도 새로 잡히는 오류가 없습니다(ADR 0002 2.1).

**적용한 것: 보정도 원장 INSERT로만 (Stripe).** 기존 WeFin은 불일치를 기록만 하고, 고치는 방법은 정해 두지 않았습니다. Stripe처럼 사람이 원인을 확인한 뒤 원장에 조정 항목을 추가하는 관리자 API를 넣었습니다(`POST /api/admin/reconciliation/adjustments`, `CashLedgerType.ADJUSTMENT`, V59).
- 원장이 빠진 경우: 잔고는 두고 원장에만 조정 항목을 추가합니다.
- 잔고가 잘못 바뀐 경우: 원장 없이 바뀐 금액을 먼저 원장에 인정하고, 그 금액을 되돌리는 조정을 잔고와 함께 반영합니다. 두 줄이 남아 무엇을 어떻게 고쳤는지 추적됩니다.
- 사유(memo)는 서비스와 DB 제약 양쪽에서 필수입니다. 조정과 주문이 동시에 잔고를 바꾸지 않도록 주문과 같은 계좌 락을 잡습니다.
- 테스트: 원장 누락 조정 뒤 대사 일치, 잔고 오류를 두 줄 조정으로 되돌린 뒤 원래 잔고와 대사 일치, 사유 없는 조정과 잔고 초과 회수 거절, DB 제약 확인 (통합 3개, 컨트롤러 2개).

## 3. 외부 API 장애 격리 (ADR 0003)

**같은 점.**
- 토스 Gateway 글은 서킷 브레이커의 목적을 느린 서비스에 요청을 더 보내지 않아 지연이 퍼지지 않게 하는 것으로 설명합니다. WeFin이 한투 시세에 서킷을 건 이유와 같습니다.
- 우아한형제들 설정 점검 규칙은 Hikari `connection-timeout`을 3초로 권장합니다. WeFin도 3초입니다(시세를 받은 뒤 커넥션을 기다리다 체결 가격이 오래되지 않게).

**다른 점과 이유.**
- 토스는 서킷을 Gateway와 각 서비스에 걸고 Route나 기능 단위로 나눕니다. WeFin은 서비스가 하나라 Gateway가 없고, 외부 의존도 한투 시세 하나라 그 호출 하나에만 겁니다. **적용하지 않음.**
- 토스 결제 원장 글은 원천사(카드사) 타임아웃으로 원천사는 승인됐는데 토스는 실패로 남는 문제를 망취소로 풀었습니다. WeFin의 한투 호출은 시세 조회라 타임아웃이 나도 한투 쪽에 남는 상태가 없습니다. **해당 없음.**

**적용 검토: 타임아웃 정렬 (토스).** 토스는 결제 체인에서 앞단 서버의 타임아웃이 뒷단 처리 시간보다 짧아, 승인은 됐는데 가맹점은 실패로 받는 문제를 겪었습니다. 뒷단 최대 처리 시간에 맞춰 앞단 타임아웃을 다시 잡아 해결했습니다. WeFin에도 같은 구조가 있는지 계산했습니다.

| 구간 | 최대 |
|---|---|
| 멱등키 선점 (커넥션 대기) | 3초 |
| 한투 시세 (커넥션 1초 + 리드 2초) | 3초 |
| 주문 트랜잭션 (커넥션 대기) | 3초 |
| 합계 (풀이 가득 찬 최악) | 약 9초 |
| 프론트 axios 타임아웃 | 5초 |

평소에는 시세 3초 이내 + DB 수 ms라 5초 안에 끝납니다. 하지만 커넥션 풀이 가득 찬 상황에서는 서버가 5초 뒤에 주문을 커밋할 수 있고, 사용자는 실패를 봅니다. 토스 글과 같은 어긋남입니다.

WeFin은 이 경우를 멱등키로 처리합니다. 클라이언트가 같은 키로 다시 보내면 커밋된 첫 응답을 받아 주문 성사 여부를 알 수 있습니다(ADR 0001). 서버 타임아웃을 5초 안으로 줄이는 방법도 있지만, 커넥션 대기를 더 줄이면 평소의 짧은 대기도 실패로 바뀝니다. 그래서 **서버 값은 그대로 두고, 프론트는 타임아웃이 나면 같은 키로 재시도하는 것을 규칙으로 정했습니다.** 프론트는 팀 레포라 이 포크에서 고치지 않았고, 필요한 변경은 ADR 0001 4절에 남겼습니다.

## 4. 잔고 차감 동시성 (design-history 1절)

**같은 점.**
- G마켓은 재고 차감을 `WHERE 재고 >= 수량` 조건부 UPDATE 한 문장으로 처리합니다. WeFin의 원자적 UPDATE와 같은 방식입니다.
- 컬리는 여러 상품 재고를 한 트랜잭션에서 차감하다 락 순서가 엇갈려 데드락이 났고, 차감 대상을 정렬해 같은 순서로 잠가 해결했습니다. WeFin이 매수·매도 락 순서를 계좌 → 보유종목으로 통일한 것과 같습니다.

**다른 점과 이유.**
- G마켓 글은 영향받은 행 수만 봐서 어떤 상품이 부족한지 모른다는 한계를 적었습니다. WeFin은 계좌 하나만 차감해서, 0행이면 계좌가 있는지만 다시 확인해 계좌 없음과 잔고 부족을 구분합니다.
- 두 글 모두 락 방식끼리 같은 조건에서 비교한 수치는 없습니다. WeFin은 비관적·낙관적·원자적 UPDATE를 같은 스키마에서 동시 1~50건으로 측정하고, 잔고 부족 경계도 따로 확인했습니다.
- 매도 입금, 평단 재계산처럼 여러 값을 함께 봐야 하는 경로는 조건부 UPDATE 한 문장으로 표현하기 어려워 비관적 락을 유지했습니다. G마켓은 다중 상품을 JOIN UPDATE로 처리했지만, WeFin의 평단 재계산은 기존 보유 수량과 평단을 읽어 계산해야 해 같은 방식을 쓰기 어렵습니다.
