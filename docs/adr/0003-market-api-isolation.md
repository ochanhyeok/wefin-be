# ADR 0003. 외부 시세 API 장애 격리

- 상태: 채택 (2026-11-25)
- 관련 커밋: `bb535ba9` (phase3/market-isolation)
- 측정: `./gradlew benchmark --tests '*MarketOutageBenchmarkTest'`

## 1. 문제

시장가 매수·매도는 `@Transactional` 메서드 안에서 현재가를 조회했다.

```
OrderService.buyMarket  ← 트랜잭션 시작 (DB 커넥션 획득)
  ├─ marketPriceProvider.getCurrentPrice()   ← 캐시(5초) 없으면 한투 HTTP 호출
  ├─ 잔고 차감, 주문·체결 저장 ...
  └─ 커밋 (커넥션 반납)
```

캐시에 없는 종목이면 한투 응답을 **DB 커넥션을 쥔 채** 기다린다. HTTP 설정은 연결 타임아웃 없음, 응답 타임아웃 5초였다.
같은 종목을 동시에 요청한 스레드는 첫 요청의 결과를 최대 10초 기다린다. 커넥션 풀은 10개다.

한투가 느려지면 주문 스레드들이 커넥션을 다 쥐고 기다리게 된다. 그러면 계좌 조회처럼 **한투와 무관한 요청도 커넥션을 얻지 못해** 같이 느려진다.
외부 API 하나의 지연이 DB 커넥션 풀을 거쳐 서비스 전체로 번지는 구조였다.

중간점검(2026-11-25)에서 멱등 설계의 트랜잭션 타임아웃(10초)을 다시 보다가 발견했다. Spring의 트랜잭션 타임아웃은 SQL을 실행할 때만 검사되므로 HTTP 대기 중에는 동작하지 않는다.

## 2. 측정 방법

`MarketOutageBenchmarkTest`. 한투를 흉내 내는 로컬 HTTP 서버(JDK `HttpServer`)가 시세 응답을 일부러 늦춘다.

- 캐시에 없는 20개 종목을 20개 스레드가 동시에 시장가 매수 (1차)
- 그동안 주문과 무관한 계좌 조회(읽기 트랜잭션)를 100ms 간격으로 20회 실행해 응답 시간 기록
- Hikari 풀의 사용 중 커넥션과 대기 스레드를 20ms마다 기록
- 1차가 끝나면 같은 20건을 한 번 더 (2차, 서킷 브레이커 효과 확인)

수정 전 코드는 `git worktree`로 커밋 `d843404b`를 꺼내 같은 벤치마크를 돌렸다. 각 시나리오 1회 실행이라 수십 ms 단위 차이는 오차로 본다.

## 3. 결정

### 3.1 시세 조회를 트랜잭션 밖으로

`MarketOrderFacade`(트랜잭션 없음)가 현재가를 먼저 조회하고, `OrderService`는 가격을 인자로 받아 트랜잭션 안에서는 DB 작업만 한다.

```
MarketOrderFacade.buyMarket   (트랜잭션 없음)
  ├─ 멱등 선점                    REQUIRES_NEW, 짧게 커밋
  ├─ 현재가 조회                  ← 한투를 기다리는 동안 커넥션 없음
  └─ OrderService.buyMarket(.., price, key)   트랜잭션: 잔고·주문·체결·원장·멱등 완료
```

조회와 체결 사이에 가격이 바뀔 수 있는 것은 이전과 같다. 이전에도 조회 직후 체결했고, 트랜잭션 안에서 조회한다고 가격이 고정되지 않는다.

달라진 점이 하나 있다 (PR #10 재리뷰). 이전에는 커넥션을 얻은 뒤 시세를 읽었으므로 커넥션 대기 시간이 가격의 나이에 들어가지 않았다. 지금은 시세를 먼저 받고 커넥션을 기다리므로, 풀이 고갈되면 기다리는 만큼 가격이 오래된다. HikariCP 기본 대기 상한이 30초라 최악에는 30초 전 가격으로 체결될 수 있었다.
대기 상한을 3초로 줄였다(`spring.datasource.hikari.connection-timeout`). 시세 화면·주문이 원래 공유하는 시세 캐시가 5초라, 주문 가격의 나이는 원래도 최대 5초였다. 여기에 커넥션 대기 3초를 더한 값이 상한이고, 넘으면 주문은 실패하고 멱등 선점이 풀려 재시도할 수 있다.
관측 시각을 주문 서비스까지 넘겨 허용 시간을 넘으면 다시 조회하는 방식도 검토했다. 허용 시간을 정하는 가격 정책이 먼저 필요하고, 캐시 5초가 이미 같은 역할을 하고 있어 보류했다.
시세 조회가 5xx로 실패하면 ADR 0001 규칙대로 멱등 선점이 풀려 같은 키로 재시도할 수 있다.

### 3.2 타임아웃: 연결 1초, 응답 2초

정상 응답은 수십 ms다. 2초 넘게 걸리는 시세로 시장가 주문을 체결하기보다 거절하는 편이 낫다고 봤다.
**트레이드오프:** 이전에는 한투가 3초 걸려도 6초 뒤 주문이 성공했다. 지금은 2초에 거절한다. 사용자는 실패를 받지만 서비스 전체는 멈추지 않는다.

### 3.3 서킷 브레이커 (Resilience4j)

| 설정 | 값 | 이유 |
|---|---|---|
| 판단 구간 | 최근 10건 | 한투 호출량이 많지 않아 시간 기준보다 건수 기준이 안정적 |
| 최소 호출 수 | 5 | 한두 건 실패로 열리지 않게 |
| 실패율 / 지연 비율 | 50% / 50% (1.5초 이상) | 타임아웃 전이라도 느린 호출이 절반이면 연다 |
| 열림 유지 | 10초 | 그동안 한투를 부르지 않고 바로 503 |
| 반열림 시험 호출 | 3건 | 성공하면 닫고, 실패하면 다시 연다 |

브레이커가 없으면 장애 동안 모든 요청이 2초씩 기다린 뒤 실패하고, 한투에는 재시도가 계속 몰린다.

**응답 검증도 브레이커 안에서 한다 (PR #10 재리뷰).** 한투는 호출 한도 초과 같은 업무 오류를 HTTP 200 + `rt_cd != "0"`으로 돌려준다. 원래는 브레이커가 HTTP 호출만 감싸고 본문은 밖(`MarketService`)에서 변환했기 때문에, 이런 응답은 브레이커에 성공으로 세어져 회로가 열리지 않았다. 이제 `rt_cd`, `output`, 현재가 필드를 브레이커 안에서 확인하고 실패면 `MARKET_API_FAILED`를 던진다.

**오래된 가격(stale)으로 대체하지 않은 이유:** 시세 화면은 몇 초 전 가격을 보여줘도 되지만, 시장가 주문을 오래된 가격으로 체결하면 사용자는 실제와 다른 가격에 사게 된다. 주문 경로에서는 거절이 맞다.

- 수정 전에는 한투 지연이 커질수록 무관한 조회가 그만큼 늦어졌다 (1초 지연 → 1.2초, 3초 → 3.0초, 무응답 → 4.9초). 풀 10개가 모두 차고 대기 스레드가 11개까지 쌓였다.
- 수정 후에는 한투 상태와 관계없이 무관한 조회가 100ms 안쪽이다.
- 1초 지연에서 매수 p50이 절반으로 줄었다. 이전에는 커넥션 10개를 쥔 10건이 한투를 기다리는 동안 나머지 10건이 커넥션을 기다려 대기가 두 번 겹쳤다.
- 정상 시나리오의 차이(68ms 대 16ms)는 1회 측정의 편차로 본다. 반복 측정은 하지 않았다.

`MarketIsolationTest` (일반 테스트, 실제 HTTP 클라이언트 + 로컬 스텁)
- 한투 500 응답 5회 → 회로 열림 → 다음 주문은 한투 호출 없이 500ms 안에 503, 멱등 선점은 풀림
- 응답 5초 지연 → 1.5~3초 안에 503
- 반열림에서 시험 호출 3건 성공 → 회로 닫힘
- HTTP 200 + 업무 오류(`rt_cd = "1"`) 5회 → 회로 열림, 주문 0건
- 커넥션 풀(10)보다 많은 매수 15건이 1초 지연 시세를 기다리는 동안 계좌 조회 5회 모두 300ms 미만. 시세 조회가 트랜잭션 안으로 돌아가는 회귀를 벤치마크 없이 잡는다

벤치마크 보고서에는 무관한 조회의 성공/실패 수를 따로 적는다. 빠르게 실패한 조회를 정상 응답으로 오인하지 않기 위해서다.

### 타임아웃 정렬 검토 (2026-11-26)

토스 결제 원장 글은 앞단 서버의 타임아웃이 뒷단 처리 시간보다 짧아 "승인됐는데 실패로 응답"하는 문제를 다룬다. WeFin 주문은 커넥션 풀이 가득 찬 최악의 경우 선점 대기 3초 + 시세 3초 + 주문 커넥션 대기 3초로 약 9초가 걸릴 수 있고, 프론트 axios 타임아웃은 5초다. 서버 값을 5초 안으로 줄이면 평소의 짧은 대기까지 실패로 바뀌어, 서버 값은 그대로 두고 타임아웃을 "같은 키로 재시도"로 다루도록 ADR 0001 4절에 정했다. 비교 전체는 [references.md](../references.md) 3절.

## 5. 남은 것

- `HantuTokenManager.getAccessToken()`이 `synchronized`이고 실패 시 1초 간격 3회 재시도한다. 토큰 갱신이 막히면 모든 시세 호출이 그 뒤에 줄 선다. 시세 호출과 토큰 갱신을 분리해야 한다.
- 일일 스냅샷 배치(`SnapshotPersistenceService`)도 계좌별 트랜잭션 안에서 시세를 조회한다. 장 마감 후 배치라 사용자 요청과 겹치지 않아 우선순위를 낮췄다.
- 서킷 브레이커 상태는 인스턴스마다 따로다. 서버가 여러 대면 각자 5건씩 실패해야 열린다.
- 브레이커 상태 변화는 로그로만 남는다. 메트릭(Micrometer)과 알림은 없다.
