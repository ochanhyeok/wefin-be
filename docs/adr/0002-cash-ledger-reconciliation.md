# ADR 0002. 현금 원장과 일일 대사

- 상태: 채택 (2026-11-25)
- 관련 커밋: `83f3fdc6` (phase2/ledger)
- 참고: Martin Kleppmann, *Accounting for Computer Scientists*

## 1. 배경

계좌 잔고(`virtual_account.balance`)는 주문 경로마다 직접 더하고 빼는 숫자 하나였다.
동시성 테스트로 "잔고가 음수가 되지 않는다"는 확인했지만, 운영 중에 잔고가 틀어지면 두 가지에 답할 수 없었다.

1. **틀어졌다는 걸 어떻게 아나?** 잔고 하나만 있으면 비교할 대상이 없다.
2. **왜 이 값이 됐나?** 어떤 주문이 얼마를 움직였는지 남은 기록이 없다. 체결 내역(trade)은 있지만, 지정가 예약금·정정 차액·취소 환불·퀘스트 보상은 체결이 아니라서 trade에 없다.

잔고를 바꾸는 경로는 10개였고, 서로 다른 서비스 세 곳(OrderService, LimitOrderService, LimitOrderMatchingService)과 VirtualAccountService에 흩어져 있었다.

| 경로 | 위치 | 잔고 변화 |
|---|---|---|
| 계좌 개설 | VirtualAccountService.createAccount | +1,000만 |
| 시장가 매수 | OrderService.buyMarket | -(체결금액 + 수수료) |
| 시장가 매도 | OrderService.sellMarket | +(체결금액 - 수수료 - 세금) |
| 지정가 매수 접수 | LimitOrderService.buyLimit | -(주문가 × 수량 + 수수료) 예약 |
| 지정가 매수 체결 | LimitOrderMatchingService | +(예약금 - 실제 비용) 차액 환불 |
| 지정가 매도 체결 | LimitOrderMatchingService | +(체결금액 - 수수료 - 세금) |
| 미체결 매수 취소 | OrderService.cancelOrder | +남은 예약금 |
| 미체결 매수 정정 | OrderService.modifyOrder | ±예약금 차액 |
| 퀘스트 보상 | UserQuestService → depositBalance | +보상 |
| (원장 도입 전 잔고) | V57 마이그레이션 | 현재 잔고 |

## 2. 결정

### 2.1 단식 원장 (append-only)

잔고를 바꾸는 모든 경로가 **같은 트랜잭션에서** `cash_ledger`에 한 줄을 남긴다. 입금은 +, 출금은 -.
한 번 쓴 줄은 수정·삭제하지 않는다. 잔고는 원장 합계의 캐시가 된다.

**복식부기를 택하지 않은 이유**
복식은 모든 이동을 차변·대변 쌍으로 남겨 "합이 항상 0"이라는 불변식을 얻는다. 은행 간 이체나 정산처럼 돈이 시스템 안의 두 계정 사이를 오가는 경우에 강하다.
이 서비스의 현금은 사용자 계좌와 "시장(외부)" 사이만 오간다. 상대 계정이 항상 같아서, 복식으로 바꿔도 새로 잡히는 오류가 없고 테이블·쿼리만 두 배가 된다.
사용자 간 송금이나 수수료 수익 계정이 생기면 복식으로 옮긴다.

**같은 트랜잭션을 강제하는 방법**
`CashLedgerService.record()`는 `@Transactional(propagation = MANDATORY)`다. 진행 중인 트랜잭션 없이 부르면 `IllegalTransactionStateException`이 난다.
원장만 커밋되고 잔고는 롤백되거나, 그 반대가 되는 어긋남을 호출 실수로도 만들 수 없다.

**잔고 직후 값(balance_after)은 저장하지 않았다**
시장가 매수의 잔고 차감은 원자적 UPDATE(`balance = balance - :amount WHERE balance >= :amount`)라서, 차감 직후 잔고를 기록하려면 경로마다 한 번 더 읽어야 한다.
대사에는 합계만 있으면 되므로 읽기를 늘리지 않았다. 특정 시점의 잔고는 그 시점까지의 원장 합계로 다시 계산할 수 있다.

### 2.2 대사 두 가지

| 대사 | 비교 | 잡는 것 |
|---|---|---|
| 계좌 대사 | 잔고 = 원장 합계 | 원장을 거치지 않은 잔고 변경, 원장 기록 누락 |
| 주문 대사 | 끝난 주문(FILLED/CANCELLED)의 원장 합계 = 체결 내역 기준 현금 이동 | 환불·정정 계산 오류, 주문 경로의 원장 누락 |

주문 대사의 기대값:
- 매수: -(체결금액 + 수수료)
- 매도: +(체결금액 - 수수료 - 세금)
- 체결 없이 취소: 0

지정가 매수는 예약 → 정정 → 체결 환불(또는 취소 환불)로 여러 줄이 쌓이지만 합은 위와 같아야 한다.
계좌 대사만으로는 "잔고와 원장이 둘 다 같은 만큼 틀린" 경우(환불 금액 계산 오류)를 못 잡는다. 주문 대사는 원장을 체결 내역이라는 독립된 기록과 맞춰본다.

**주문이 들어오는 중에 돌려도 되는 이유**
각 검사는 SQL 한 문장이다. PostgreSQL은 한 문장을 한 시점의 스냅샷으로 읽고, 잔고와 원장은 같은 트랜잭션에서 커밋된다.
그래서 "잔고는 반영됐는데 원장은 아직" 같은 중간 상태가 보이지 않는다. 장 마감 후에만 돌릴 필요가 없다.
테스트: 4개 계좌가 계속 매수하는 동안 대사를 10번 돌려 불일치 0건.

### 2.3 불일치는 기록만 하고 고치지 않는다

불일치가 나면 `reconciliation_mismatch`에 (계좌, 주문, 기대값, 실제값)을 남기고 에러 로그를 남긴다.
자동으로 잔고를 원장에 맞추지 않는다. 원장 기록이 빠진 것인지 잔고가 틀린 것인지는 원인을 봐야 안다. 확인 없이 돈을 움직이면 오류가 하나 더 생긴다.

### 2.4 실행 관리 (작성가이드 7번: 자동화)

| 상황 | 처리 |
|---|---|
| 정기 실행 | 평일 16:10 (장 마감 15:30, 일일 스냅샷 15:40 이후) |
| 여러 인스턴스가 동시에 실행 | `reconciliation_run`에 `status = 'RUNNING'` 부분 유니크 인덱스. 두 번째 INSERT가 막혀 409. 분산 락(ShedLock, Redis) 없이 DB 제약으로 해결 |
| 실행 중 서버가 죽음 | RUNNING이 30분 넘으면 다음 실행 시작 시 FAILED로 정리. 정리하지 않으면 유니크 인덱스 때문에 이후 대사가 영원히 시작되지 않는다 |
| 죽은 줄 알았던 실행이 다시 깨어남 | 종료 기록 전에 실행 행을 `SELECT ... FOR UPDATE`로 잠그고 RUNNING인지 확인. 이미 FAILED면 성공으로 덮지 않고 검사 트랜잭션(불일치 행 포함)을 롤백한다. 실패 기록도 RUNNING일 때만 남겨 원래 중단 사유를 덮어쓰지 않는다 |
| 시작 자체가 실패 (DB 연결 등) | 실행 기록이 없으므로 스케줄러가 예외를 로그로 남긴다 |
| 검사 중 예외 | 시작·검사·종료를 각자 트랜잭션으로 나눴다. 검사가 롤백돼도 FAILED와 원인은 남는다 |
| 다시 돌리기 | `POST /api/admin/reconciliation/runs`. 대사는 읽고 기록만 하므로 몇 번을 다시 돌려도 안전하다 |
| 결과 확인 | `GET /api/admin/reconciliation/runs` |

### 2.5 원장 도입 전 데이터

- 기존 계좌: 마이그레이션 시점 잔고를 `OPENING_BALANCE` 한 줄로 기록. 그 이전 이동은 복원할 수 없으므로, 대사는 도입 이후 변경만 보장한다.
- 기존 주문: 예약 출금이 원장에 없어 주문 대사에서 틀리게 잡힌다. `cash_ledger_meta.introduced_at` 이후 생성된 주문만 검사한다.
- 도입 전에 접수돼 도입 후 체결된 지정가 매수: 예약금은 이미 잔고에서 빠졌고 기초 잔액에 반영됐다. 체결 환불은 원장에 남는다. 계좌 대사는 맞고, 주문 대사는 시간 조건으로 제외된다.

## 3. 관리자 API 보호

`AdminAuthorizationFilter`는 `/api/admin/accounts`만 관리자 권한을 검사하고, `SecurityConfig`는 나머지 `/api/admin/**`를 `permitAll`로 둔다 (팀 커밋 `7bba5bcc`에서 의도적으로 좁힘).
대사 실행 API를 이 설정에 그대로 두면 누구나 대사를 실행할 수 있어서, 검사 경로 목록에 `/api/admin/reconciliation`을 추가하고 `authenticated`로 바꿨다.
경로 판정은 요청 URI에서 context path를 뺀 값으로 한다. 원래는 URI 전체를 비교해서, 비루트 context path(`/wefin/api/admin/...`)로 배포하면 검사가 통째로 빠졌다 (PR #9 재리뷰).
다른 `/api/admin/**`(뉴스 배치, 시세 관리 등)가 인증 없이 열려 있는 문제는 팀 결정이라 이 포크에서 바꾸지 않았다. 따로 공유할 사항이다.

## 5. 한계와 다음 단계

- V57은 기초 잔액 적재와 원장 기록 시작을 한 번에 한다. 구버전 인스턴스가 함께 떠 있으면 그 인스턴스의 잔고 변경은 원장 없이 커밋돼 불일치로 남는다. 이 포크는 단일 인스턴스이고 운영 배포 이력이 없어 그대로 뒀다. 운영에 적용한다면 구버전을 모두 내린 뒤(쓰기 중단 구간) V57과 새 버전을 올리거나, 새 버전 배포 완료 후 `OPENING_BALANCE`를 다시 적재해야 한다 (PR #9 재리뷰).

- 매 실행마다 원장 전체를 합산한다. 원장이 커지면 일별 마감 잔액(체크포인트)을 남기고 그 이후분만 더하는 방식으로 바꿔야 한다.
- 보유 수량(portfolio)은 원장 대상이 아니다. 수량도 체결 내역과 대사할 수 있다.
- 불일치 알림은 로그뿐이다. 슬랙 등 외부 알림은 없다.
